# Git & PR Workflow

This project uses a PR-per-functionality flow. `main` stays roughly empty/minimal until things are proven, then fills deliberately via reviewed PRs. **All work is committed and pushed as the human — never with any Claude/AI attribution.**

---

## One-time setup (do this first)

Configure git as the human (replace with your real details):
```bash
git config user.name  "Your Name"
git config user.email "you@example.com"

# Ensure NO AI co-author/attribution templates are active:
git config --global commit.gpgsign false          # optional
git config --unset-all commit.template 2>/dev/null || true

# Authenticate GitHub as you (use ONE of):
# (a) GitHub CLI:  gh auth login   (then gh acts as you)
# (b) SSH key added to your GitHub account
# (c) a personal access token stored in a credential helper
```

**Rule:** every commit author = you. Every PR author = you. No "Generated with…", no "Co-Authored-By: Claude", no AI mentions anywhere.

---

## Branch model

- **`main`** — protected, roughly empty/minimal. Only proven, reviewed functionality lands here. Never commit directly to `main`.
- **feature branches** — one per functionality/stage-chunk. Named:
  - `stage-0/<thing>` e.g. `stage-0/scaffold`, `stage-0/schemas`
  - `stage-1/<thing>` e.g. `stage-1/vllm-serving`, `stage-1/unsloth-smoke`, `stage-1/lab-state-machine`
  - `stage-2/<thing>` e.g. `stage-2/web-verifier`, `stage-2/verifier-assurance`
  - `fix/<thing>`, `docs/<thing>`, `chore/<thing>` for non-stage work.

Keep each branch/PR **focused on one functionality.** Many small PRs > one huge PR.

---

## The flow (every piece of work)

```bash
git switch main && git pull
git switch -c stage-1/vllm-serving          # new focused branch
# ... do the work, commit after each working step ...
git add -A
git commit -m "serving: vLLM serves Qwen3-30B-A3B FP8 on GB10"   # human voice, no AI mention
git push -u origin stage-1/vllm-serving
gh pr create --fill --base main             # opens PR AS YOU; fill the template
# → the HUMAN reviews and merges. Claude Code does NOT merge.
```

**Claude Code's limit:** it may create branches, commit, push, and open PRs (as you). It must **not** merge to `main`. You review and click merge. (Docs-only PRs also wait for you unless you say otherwise.)

---

## Commit message style

- Imperative or plain factual, human engineering voice.
- Format: `<area>: <what changed>` — e.g. `verifier: add remediation hole-closed + service-alive check`.
- No AI attribution, no emoji unless you want them, no "generated by".
- One logical change per commit.

---

## PR rules

- Title: `<area>: <summary>` (e.g. `stage-1: vLLM serving + throughput baseline`).
- Body: fill `.github/pull_request_template.md` — link the stage + DoD items, list tests, note any `DECISIONS_TO_REVISIT.md` entries added.
- CI (lint + unit + assurance tests) must pass before you merge.
- Squash-merge preferred to keep `main` history clean (your call).
- Delete the branch after merge.

---

## When `main` gets filled

`main` fills only as functionality is PROVEN:
- Stage 0 scaffold + schemas → first PRs into `main` (these are safe foundations).
- Stage 1 serving/training proof → merged once confirmed on the cloud GB10.
- Stage 2 web verifier + the proof → merged once the verifier assurance passes and one generation beats baseline.
- Phase 2 → merged only after the Stage-2 proof holds.

Until a thing is proven, it lives on its branch/PR, not on `main`.

---

## Decisions-to-revisit protocol

Whenever a choice is made because of a *current constraint* that will later change:
1. Add an entry to `DECISIONS_TO_REVISIT.md` (what / why now / trigger / action on trigger).
2. Open a GitHub issue:
   ```bash
   gh issue create --title "Revisit: <short title>" \
     --body "See DECISIONS_TO_REVISIT.md. Trigger: <condition>." \
     --label "revisit-on-dgx"
   ```
3. Reference the issue number in the `DECISIONS_TO_REVISIT.md` entry.

When the trigger fires (e.g. the physical DGX is bought), work through the open `revisit-on-dgx` issues and close each as it's resolved.
